What changed recently. Full commit-by-commit history lives on GitHub — and the panel itself shows incoming changes under Update before you upgrade.

Latest — The docs site now checks itself against the panel

  • Five endpoints were documented nowhere: /api/ai/test, /api/telegram/test, /api/api-tokens/self-test, /api/blocklist/porn and /api/tunnel-settings all existed, all had a button in the panel, and none of them appeared in the API reference. The prose described what they do; a bot author had no endpoint to call.
  • Seventeen of the nineteen server settings were named only by their label: the page said “Obfuscated host”, “REALITY SNI list” and “Block direct IP”, so the name you need for GET /api/settings, a backup or a hand-edited row — obfuscated_host, reality_sni, block_direct_ip — appeared nowhere. Configuration now carries a table of all nineteen, with defaults and what each one changes.
  • The admin dashboard was not written down at all: the five cards, what “Active” counts and — the part that surprises everyone — what the small line under it counts instead (expiring within 7 days, not started, out of volume), the CPU/memory/disk card and the five newest accounts now have a section of their own.
  • A suite reads the code and the site and compares them: every sidebar section must have a docs destination that really exists, every registered /api endpoint must appear in the reference, and every stored setting key must appear by name. Adding an endpoint without writing it down now turns the suite red. It was proved by injection: a fake route and a fake setting key each fail the check, and the restored tree passes again.

v1.15.54 — The rule that decides who a request is, now guarded

  • The rule that decides who a request is, now guarded. client_ip() answers one question - whose request is this? - and the answer goes into the rate limiter it spends, the audit row it writes and the admin session it belongs to. It is the function that makes "we rate-limit by IP" mean anything, and it had no test.
  • The rule, stated once: the peer is NOT trusted, so the header is ignored entirely and the socket address is the answer - a client that forges X-Forwarded-For gains nothing. The peer IS trusted, so the header is walked from the RIGHT and the first hop that is not itself trusted is the answer: the hop the proxy appended is the real client, and anything the client put in front of it is ignored.
  • That second case depends on the proxy APPENDING. A proxy that REPLACES the header hands the client the last word on its own identity, and the panel cannot tell. The installer's nginx appends ($proxy_add_x_forwarded_for), so the documented install is correct - but that was never written down where an operator who adds their own proxy would read it. Now it is, in the configuration reference, in four languages.
  • Testing it needed a synthetic peer. An end-to-end probe always connects from the loopback, and the loopback is exactly the peer the panel TRUSTS, so such a probe can only ever exercise the trusted case and says nothing about the one an attacker is in. The first attempt measured nothing: it read the header's effect on the audit trail, whose rows were older than the calls, and the wrong passwords were seven characters long and answered 422 before the limiter was ever charged. client_ip_test.py exercises the rule directly, with the peer as an argument. The runner now runs 60 suites.

v1.15.53 — An MCP tool call is attributed to the caller who made it

  • An MCP tool call is attributed to the caller who made it. The MCP transport forwards a tool call into the panel's own API, in-process, and it forwards the CALLER'S TOKEN - so the scope check is the panel's own and the blast radius is right. What it did not forward was the caller's ADDRESS: the ASGI scope hard-coded "client": ("127.0.0.1", 0), so every forwarded call claimed to come from the loopback.
  • Two things followed, and both were measured rather than reasoned: the audit trail could not attribute the action - one MCP call that created a customer wrote MCP_CALL ip=203.0.113.9 and USER_CREATE ip=127.0.0.1, the same operation with two addresses in one trail, and "who added this customer?" had no answer beyond "the loopback". And the per-IP rate limiters of the FORWARDED routes keyed on that single address, so every MCP client in the world shared one bucket, together with the operator's own same-host requests through nginx.
  • The address is now passed down, and the forwarded call carries the caller's own. A bot-scoped token still cannot use MCP at all, and the scope check is still the panel's own. Measuring this needed a caller that was NOT on the loopback, and the first attempt measured nothing: the probe connected from 127.0.0.1, so the direct call and the forwarded one BOTH recorded 127.0.0.1 and looked identical. The panel trusts X-Forwarded-For from the loopback - the same-host nginx case, and the installer's default - so one operation's two rows can be compared. The runner now runs 59 suites.

v1.15.52 — The restore report says what was LOST, not what was refused

  • The restore report says what was LOST, not what was refused. The restore is the operator's disaster recovery, so its report is read when something has already gone wrong. And it was mixing four different things under one number.
  • Measured on a live panel, restoring 101 customers onto a panel that already had its own nodes and inbounds, the restore answered added_users: 101, skipped: 13, restored_snodes: 0, restored_inbounds: 0 - and NONE of the thirteen were lost. Six were server nodes and four were inbounds whose names ALREADY EXISTED, and the panel still has them, visible, in the menu. The other three were the origin keys, reset on purpose because an unsigned backup does not get to repoint a deployment's public identity. An operator reading that concludes they lost thirteen customers.
  • And what was hidden in the same bucket is what the operator really needed to know: a REALITY key or a Telegram chat id that belonged to ANOTHER server and could not be moved. That is a real loss - every customer's link is broken until they re-provision - and it looked exactly like the harmless cases. So the report now separates them, the way refused already did for credentials: skipped for rows genuinely lost, already_present for rows that were already there, refused for credentials, skipped_settings_refused for the origin keys, and skipped_settings_lost for the ones that need the operator's attention.
  • The measurement of it was wrong three times first, and each wrong version looked like a catastrophe. Copying the database file over a live WAL-mode one left a stale sidecar and a database that reported zero customers; reading a 401 as "the customers are missing" when a restore deliberately revokes every session; and reading a 429 from the rate-limited customer list as an empty list. The suite works on a COPY of the instance, so the real one is never touched. The runner now runs 58 suites.

v1.15.51 — A missing master key must not destroy the data silently

  • A missing master key must not destroy the data silently. The panel was careful about an EXISTING but unusable key: it refuses to start, because replacing the master key would sign out every session and make every encrypted credential permanently undecryptable. A missing key took the other branch, and a new one was generated.
  • Measured on a live panel: delete instance/secret.key, keep instance/zefira.db, and the panel started without a word, showed all 100 customers, and every encrypted field among them was gone - the REALITY key, the Telegram token, the AI key and every customer's private config - while the panel looked perfectly healthy. The code's own comment said "delete it to intentionally start a fresh instance", which is only true when the DATABASE is fresh too.
  • So a missing key plus an existing database is a LOST KEY, and the panel now says so and refuses to start, naming what would be destroyed and how to get out of it. A genuinely fresh instance - no key and no database - still starts and creates both, and an empty database file is not treated as data. The check reads the database read-only, never raises, and stands aside when the data lives in an external DATABASE_URL rather than in the local file.
  • The suite works on a COPY: it copies the application and the instance directory to a temporary directory, so the real instance is never at risk, and it checks all four cases - because a guard that refuses to start a brand-new panel is just as broken as one that never refuses. Four mutations prove it goes red. The runner now runs 57 suites.

v1.15.50 — The logs say which request they belong to

  • The logs say which request they belong to. The panel already had half of what production troubleshooting needs: it mints a request id, echoes it on the response, and writes it into the access log. What was missing is the other half. The lines a HANDLER emits had no way to be tied to a request - a telegram notification that failed, a Host header that was refused, a restore that was skipped, a rate limiter that said no. Those are exactly the lines you want at 14:03, and they were unattributable.
  • So the id now rides on every line written inside a request, as a structured field rather than as text in the message. And there is a JSON mode for a log shipper: ZEFIRA_LOG_FORMAT=json gives one object per line with the timestamp, the level, the logger, the message and the request id. ZEFIRA_LOG_LEVEL sets the level. Both are off by default, so an existing install behaves exactly as before - the plain text format is still the default.
  • Two bugs arrived with the first attempt, and the first is the kind that takes a panel's logs down silently: logging.StreamHandler(THE_FORMATTER) passes the formatter as the STREAM, so the panel wrote a traceback on every log line instead of a log line, and nothing said so - the panel ran fine and logged nothing. The second was the context variable being reset in a finally around call_next(), so it was already cleared before the access log was written: the id was missing from the very line that exists to carry it.
  • And one measurement made honest. The update-page latency check compared a cold read against a FIXED fraction of a 1.5s network stub, so it measured the machine as much as the panel: on a loaded box the read crossed the threshold while still being plainly not waiting - the stub alone costs 1.5s. The threshold is now relative to the WARM read on the same machine, so what is asserted is that the cold path costs less than the stub MORE than the warm one does. Its own mutation, which makes the request path wait for the network, still turns it red - with a wider margin than before.
  • And the formatter never raises. A logging bug that takes the panel's logs down with it is much worse than a malformed line, so anything unexpected falls back to the plain format - and the suite checks that, because the fallback is the part nobody would notice if it did not work. logging_format_test.py starts its own panel with the variable set and reads what the panel actually wrote; four mutations prove it goes red. The runner now runs 56 suites.

v1.15.47 — The API reference finally shows what comes back

  • The API reference finally shows what comes back. Coverage was already 100% — 55 of 55 routes, each with its own method badge, in four locales — so "insufficient" could never have meant missing routes. It meant something narrower and more real: the page showed every request example and not one response body. Seven of them now, for the routes a bot actually calls.
  • Generated from a capture, not written from memory. A response shape that is subtly wrong is worse than no shape, because a developer codes against it and discovers the truth in production. So every example on the page came out of a running panel, key sets and value types both.
  • Which turned up four things a plausible example gets wrong: volume_gb is a float, not an integer. used_gb is an integer, not a float, and then becomes a float the moment usage is fractional — PATCH {"used_gb": 12.5} comes back as 12.5, not 12. A token's scopes is a single string, not an array.
  • And one that is not a type at all: GET /api/users/{id}/config does not answer JSON. It answers text/plain with the subscription document itself — one vless:// URI per line, one per configured protocol. A bot author who expected an object there would fail on the single most-requested call a reseller bot makes. A negative used_gb is a 422, not a silent clamp.
  • A guard that runs the panel, five mutations proved red: api_response_shapes_test.py is live rather than static on purpose: a static check could only compare the documentation with itself and would pass forever. It starts its own panel and compares every published example's key set and value types against what the API returns. Renaming a field, changing a type, contradicting the float case, dressing the non-JSON example up as JSON, and deleting an example all turn it red. The runner now runs 54 suites.

v1.15.45 — The audit log keeps the newest 2000 rows, and finally says so

  • The audit log keeps the newest 2000 rows, and now says so. It always did - audit() prunes on every call, with no time-based retention and no archive - but no document mentioned it, so an operator had no way to know. Measured on a running panel at the highest budget the schema allows: after 600 tool calls at 600/min an operator's own settings change was gone, a refused destructive call was gone, and MCP_CALL was 100% of what remained. That is 3.3 minutes of history at the maximum, 33 at the default 60/min. The number is unchanged - it is a trade-off with a cost on both sides, and it is the operator's call - but it is now written down, in arithmetic, in SECURITY.md.
  • A guard so it cannot drift: audit_retention_test.py reads the retention threshold out of main.py and the MCP budget out of the schema, computes both durations, and fails if the document says anything else - including if it names a second, different figure, which is what an edit-in-place produces.   • Also worth writing down: the measurement itself was wrong twice before it was right. v1.15.44 — An AI client can drive this panel

  • MCP server, both transports: a stdio server for a client that launches the panel, and a JSON-RPC endpoint at POST /api/mcp for clients that speak HTTP. Twenty-five tools covering users, nodes, inbounds, tunnels, the blocklist and the settings. Nothing new is granted — an MCP token is an ordinary full token, so every tool is something that token could already do. Added on top: an audit row per tool call, an exact confirmation string before anything destructive, and a per-token call budget. The panel installs no new dependency; the official SDK is used only to test against, in a throwaway environment outside the repository.
  • Fourteen bugs found while auditing it. A redirect could carry your token to another host: urllib replays the Authorization header on a 302, so an open redirect on the panel — or a proxy in front of it — handed a token to whatever the Location header named, and the tool call still came back looking successful. Redirects are now followed only within the origin you configured. Turning MCP off switched the HTTP transport back on: saving one setting rewrote the other two to their defaults. The switches read the wrong way round, so anything not meant to be on — the word false included — enabled MCP. The endpoint ignored token scopes, which every other route checks and refuses. The required confirmation was None when you named no customer to confirm, and the refusal told the model to send exactly that back. A bare .. became a real path segment. Server error text reached the AI, including a file path; you still see the detail, in the audit log.
  • Also: the Test button reported success without testing anything, because it asked the server a question the server answers from a constant. It now makes a real call and hands back the panel's own numbers. A reply that carried no question mark was answered anyway, and a question that happened to start with notifications/ was never answered at all, which could hang a client waiting.
  • Suites for all of it: one guard per defect, each proved by putting the original bug back and watching the guard fail — thirteen of thirteen. A guard that has never been seen to fail is not evidence. The eight MCP suites bring the runner to fifty-one, and the conformance suite exits 2 rather than 0 when it cannot build its SDK client, because a suite that could not run must never be reported as a pass.

v1.14.3 — White-hat security round: a service foothold could reach root, a backup could disarm every rate limiter, and a rebound host could take the AI provider key

  • The installer could hand a service foothold root: when install.sh is piped, bash has no script path, so the “anchor to the script’s own directory” rule silently fell back to $PWD. Running sudo bash install.sh from /opt/zefira — a tree the service account owns — made root pip install from a requirements.lock that account could rewrite, and --require-hashes trusts the hashes in that same file. A piped install now never uses the working directory, and /opt/zefira is explicitly refused as a source.
  • A crafted backup could disarm every rate limiter: trusted_proxies was importable, and it is the KEY of every per-IP limiter — login brute force, subscription, restore, QR, probe. One attacker /32 in a “customer list” backup made every later request carry an attacker-chosen X-Forwarded-For (unbounded login guesses) and wrote that value into the audit log, so the operator’s own trail pointed at a third party. Like public_url and domain, it is set in Settings only.
  • A leaked API token could replace itself: minting one required no password, so a stolen full token called the same endpoint and received an equally powerful replacement — and revoking the one token the operator could see did not lock the attacker out. Every durable-credential operation now re-prompts for the admin password (as backup, restore and update already did), a new token expires after 180 days unless you ask for otherwise, and one admin may hold at most 20.
  • A rebound AI host could receive the provider key: the base URL was validated, then urllib resolved the name again when it opened the socket. A host whose DNS an attacker controls (two answers, low TTL) passed validation, passed the “is it local, should I send the key” check, and then connected to 127.0.0.1 — handing over a live credential. The connect is now pinned to the address that was validated, with the real hostname kept for the Host header and TLS.
  • One restore request could hold a core for two hours: rows whose credentials cannot be validated are re-provisioned server-side, and an OpenVPN row mints a 2048-bit RSA key. The row cap is 10,000 and nothing bounded the work, so a 12 kB crafted file kept one core busy for close to two hours — and every mutating /api/* route answers 409 while a restore holds the lock, so the whole write plane was down for that long. Re-minting is now budgeted, and the overflow is refused and reported instead of silently dropped. Inbounds are capped too, because each one multiplies a subscription rendered on the unauthenticated path.
  • A crafted backup could repoint the assistant: the AI settings were imported, so a backup could aim the panel at an attacker’s endpoint AND plant text in the system prompt the assistant treats as an ADMIN NOTE — and the next time you asked it anything, the traffic and up to nine tool calls went to the attacker. The whole AI setup is re-entered in Settings now, like the admin credentials.
  • Snapshots were readable by every local user, and never pruned: pg_dump --file and mysqldump --result-file create their output with the process umask, so under the common 0022 the complete database — admin hashes, every customer’s private key, token hashes — was world-readable for the length of the dump. The panel now creates the file itself at 0600, and the dump and pre-update copies are pruned like the SQLite ones. On the docs side: the changelog printed its own emphasis tags as literal text, and every HTML entity in a translation printed as its own characters instead of the character it stands for, frame-ancestors in a <meta> is ignored by browsers (there is a working frame-buster instead), and a protocol-relative knowledge-base link could leave the site silently.

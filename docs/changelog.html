Changelog

What changed recently. Full commit-by-commit history lives on GitHub — and the panel itself shows incoming changes under Update before you upgrade.

Latest — The docs site now checks itself against the panel

  • Five endpoints were documented nowhere: /api/ai/test, /api/telegram/test, /api/api-tokens/self-test, /api/blocklist/porn and /api/tunnel-settings all existed, all had a button in the panel, and none of them appeared in the API reference. The prose described what they do; a bot author had no endpoint to call.
  • Seventeen of the nineteen server settings were named only by their label: the page said “Obfuscated host”, “REALITY SNI list” and “Block direct IP”, so the name you need for GET /api/settings, a backup or a hand-edited row — obfuscated_host, reality_sni, block_direct_ip — appeared nowhere. Configuration now carries a table of all nineteen, with defaults and what each one changes.
  • The admin dashboard was not written down at all: the five cards, what “Active” counts and — the part that surprises everyone — what the small line under it counts instead (expiring within 7 days, not started, out of volume), the CPU/memory/disk card and the five newest accounts now have a section of their own.
  • A suite reads the code and the site and compares them: every sidebar section must have a docs destination that really exists, every registered /api endpoint must appear in the reference, and every stored setting key must appear by name. Adding an endpoint without writing it down now turns the suite red. It was proved by injection: a fake route and a fake setting key each fail the check, and the restored tree passes again.

v1.15.48 — The switch that could not be switched off

  • The switch that could not be switched off. Measured, not reported: with block_direct_ip ON, the settings PUT that was supposed to turn it OFF was answered 403 - "Direct IP access to panel is disabled, use domain" - and the stored value stayed "1". The request that disables the switch was itself subject to the switch. An operator working over IP could tick the box and then never untick it, and an install whose domain is still the zefira.example.com placeholder had no way back at all.
  • The fix keeps the feature and drops the trap: the switch is an ANTI-SCAN measure, so an anonymous request on an IP literal is still refused - with no credential of any kind, on every spelling including 2130706433 and 0x7f000001. What changed is that a request carrying a valid session or a valid API token is let through. A scanner has neither, so it sees exactly what it saw before, and an operator who can authenticate is never locked out of their own panel. attack_test.py used to assert the opposite and worked around the lockout with a domain Host header; it now asserts both halves, and the restore no longer needs that cheat.
  • The MCP section goes above Settings, and stays there. It already was in panel.html and in the front end's MENU_IDS - and BELOW it in the server's MENU_SECTIONS, which is the tuple that gets STORED. Two places disagreed, the comment above the tuple said they had to agree, and nothing checked. The saved layout on a live install read [... "api", "settings", "mcp"]. menu_order_test.py now compares all three sources - and the dashboard's block list too - with five mutations proved red.
  • Three more found by hunting around them: a settings PUT with the four required ports and nothing else was accepted and wrote the model's DEFAULTS over everything it did not mention - the WireGuard public key was erased and all three switches went off; the four ports still refuse a body without them, as before, so the contract only ever covered half the problem. GET /api/appearance returned the layouts already parsed while the PUT wanted a string, so the obvious client - GET, change one field, PUT back - was answered 422. And the three switches came back as the strings "1" and "0" where the model declares them bool.
  • And a tool for the demo: examples/demo_data.py fills a panel with a hundred realistic customers, a spread of usage, some expired accounts and a few servers - so a screenshot or a video shows a product rather than an empty table. It is seeded, so two runs produce the same panel; it marks everything it creates and --clean removes exactly those; and it reports the panel's 120-customers-per-hour creation limit as what it is instead of pretending to have created what it did not. The runner now runs 55 suites.

v1.15.47 — The API reference finally shows what comes back

  • The API reference finally shows what comes back. Coverage was already 100% — 55 of 55 routes, each with its own method badge, in four locales — so "insufficient" could never have meant missing routes. It meant something narrower and more real: the page showed every request example and not one response body. Seven of them now, for the routes a bot actually calls.
  • Generated from a capture, not written from memory. A response shape that is subtly wrong is worse than no shape, because a developer codes against it and discovers the truth in production. So every example on the page came out of a running panel, key sets and value types both.
  • Which turned up four things a plausible example gets wrong: volume_gb is a float, not an integer. used_gb is an integer, not a float, and then becomes a float the moment usage is fractional — PATCH {"used_gb": 12.5} comes back as 12.5, not 12. A token's scopes is a single string, not an array.
  • And one that is not a type at all: GET /api/users/{id}/config does not answer JSON. It answers text/plain with the subscription document itself — one vless:// URI per line, one per configured protocol. A bot author who expected an object there would fail on the single most-requested call a reseller bot makes. A negative used_gb is a 422, not a silent clamp.
  • A guard that runs the panel, five mutations proved red: api_response_shapes_test.py is live rather than static on purpose: a static check could only compare the documentation with itself and would pass forever. It starts its own panel and compares every published example's key set and value types against what the API returns. Renaming a field, changing a type, contradicting the float case, dressing the non-JSON example up as JSON, and deleting an example all turn it red. The runner now runs 54 suites.

v1.15.46 — The MCP modules get the type annotations they shipped without

  • An assessment said type hinting was incomplete. It was, in one place, and the place was mine: the four MCP modules shipped last release with zero annotated signatures out of 34. All 34 now carry them. Every return type was measured by calling the function rather than inferred from reading it - build_call really does return a 4-tuple, split_path_and_query really does return (str, bytes) - because a guessed annotation is worse than an honest loose one.
  • The measurement doubled as a regression check: expected_confirmation("delete_user", {}) still raises ToolError rather than returning "None", and check_confirmation still names the real target. Those are two of the fourteen defects from v1.15.44, still closed after every signature in the file was rewritten.
  • And the assessment's other claims, checked rather than argued: main.py was already 94% annotated and security.py 86%, with 4 bare top-level functions between them. install.sh configures a firewall but no fail2ban, no nginx rate limiting and no log rotation. The API reference covers 100% of routes but contains no response-body examples, which is the part a bot author actually needs. Two claims - "single worker is critical" and "curl | sudo bash is unmitigated" - did not survive being measured, and the reasons are in SECURITY.md with the numbers attached.
  • A guard, proved red three ways: type_hints_test.py requires the MCP modules to stay fully annotated and forbids main.py from gaining a new unannotated top-level function. Its allowance names four functions rather than counting, so widening the allowance is itself a failure - a guard whose threshold can be moved from inside is decoration. The mutations: revert one signature, add a bare function, and widen the allowance. The runner now runs 53 suites.
  • Worth recording: the first attempt to measure whether one worker can be stalled was inconclusive and would have shipped as a pass. It used /api/update/status, which answered in 13 ms because it was cached - so nothing slow was ever in flight and "not blocked" proved nothing. The slow-client test that replaced it holds 60 connections open on purpose. Also: a return annotation cannot begin a new line after a parameter list closes in CPython, and implicitly concatenated string literals join with nothing rather than a newline - both cost an attempt here and both are now asserted in the builder script.

v1.15.45 — The audit log keeps the newest 2000 rows, and finally says so

  • The audit log keeps the newest 2000 rows, and now says so. It always did - audit() prunes on every call, with no time-based retention and no archive - but no document mentioned it, so an operator had no way to know. Measured on a running panel at the highest budget the schema allows: after 600 tool calls at 600/min an operator's own settings change was gone, a refused destructive call was gone, and MCP_CALL was 100% of what remained. That is 3.3 minutes of history at the maximum, 33 at the default 60/min. The number is unchanged - it is a trade-off with a cost on both sides, and it is the operator's call - but it is now written down, in arithmetic, in SECURITY.md.
  • A guard so it cannot drift: audit_retention_test.py reads the retention threshold out of main.py and the MCP budget out of the schema, computes both durations, and fails if the document says anything else - including if it names a second, different figure, which is what an edit-in-place produces. Four mutations prove it goes red: raising the retention in code alone, lowering the budget ceiling in code alone, editing the document's own number, and removing the pointer to the knob that changes the answer.
  • Also worth writing down: the measurement itself was wrong twice before it was right. The first version asked "is the operator's row still there?" and printed an answer derived from the row COUNT being under the cap, which is true whenever the prune works and therefore proved nothing. The second drove 4200 calls in 74 seconds - five times the ceiling the schema permits - so most were refused by the limiter before they ever reached the dispatcher, and it measured a hammering rather than a load. Both are why the figure above is 600 accepted calls, paced.

v1.15.44 — An AI client can drive this panel

  • MCP server, both transports: a stdio server for a client that launches the panel, and a JSON-RPC endpoint at POST /api/mcp for clients that speak HTTP. Twenty-five tools covering users, nodes, inbounds, tunnels, the blocklist and the settings. Nothing new is granted — an MCP token is an ordinary full token, so every tool is something that token could already do. Added on top: an audit row per tool call, an exact confirmation string before anything destructive, and a per-token call budget. The panel installs no new dependency; the official SDK is used only to test against, in a throwaway environment outside the repository.
  • Fourteen bugs found while auditing it. A redirect could carry your token to another host: urllib replays the Authorization header on a 302, so an open redirect on the panel — or a proxy in front of it — handed a token to whatever the Location header named, and the tool call still came back looking successful. Redirects are now followed only within the origin you configured. Turning MCP off switched the HTTP transport back on: saving one setting rewrote the other two to their defaults. The switches read the wrong way round, so anything not meant to be on — the word false included — enabled MCP. The endpoint ignored token scopes, which every other route checks and refuses. The required confirmation was None when you named no customer to confirm, and the refusal told the model to send exactly that back. A bare .. became a real path segment. Server error text reached the AI, including a file path; you still see the detail, in the audit log.
  • Also: the Test button reported success without testing anything, because it asked the server a question the server answers from a constant. It now makes a real call and hands back the panel's own numbers. A reply that carried no question mark was answered anyway, and a question that happened to start with notifications/ was never answered at all, which could hang a client waiting.
  • Suites for all of it: one guard per defect, each proved by putting the original bug back and watching the guard fail — thirteen of thirteen. A guard that has never been seen to fail is not evidence. The eight MCP suites bring the runner to fifty-one, and the conformance suite exits 2 rather than 0 when it cannot build its SDK client, because a suite that could not run must never be reported as a pass.

v1.15.43 — A bounty that promises nothing it cannot keep

  • The defect that made the old policy worthless: SECURITY.md carried a real disclosure policy — do not open a public issue, report through GitHub Security Advisories — and GitHub private vulnerability reporting was switched off on this repository. Measured, not assumed: the API answered {"enabled": false}. So the link in the document pointed at a button that did not exist, and the researcher who followed the advice exactly was sent to the public issue the same document had just warned them off. A policy whose only instruction is where to go, with the destination closed, is worse than no policy, because it looks like one. It is on now, and the flag was read back from GitHub rather than trusting the write.
  • What the bounty does and does not say: It promises no money, because none is funded. Naming a figure with no escrow behind it would be a promise this project cannot keep, made to precisely the people most likely to do the hard work of finding real bugs — and a broken promise to the security community costs more than no promise at all. What it grants instead is real: safe harbour, so a good-faith researcher reads the scary parts and still proceeds; permission to publish a write-up once a fix has shipped or 90 days have passed; four defined severities with concrete examples drawn from what this panel actually holds (customer WireGuard private keys, the OpenVPN client key, the L2TP PSK); and a credit in the release notes unless the reporter opts out. The four documented trade-offs — single worker by design, SQLite write serialisation, no HSM or KMS, the AI assistant sending operator-written prompts to the configured provider — are named explicitly as not-defects, so that a good-faith report on them does not go to waste. Out of scope is also stated: testing a panel you do not own, denial of service, and social engineering of the operator.
  • And a second document defect, the same disease as always: SECURITY.md opened by claiming thirty-five test suites and naming a check count for each of seven of them — `security_test.py` (120), `feature_test.py` (178), `functional_test.py` (60), `attack_test.py` (129), `attack_quota_test.py` (46), `attack_paths_test.py` (111), `frontend_bugs_test.py` (35). The runner had 42 suites by then, and every one of those figures was stale. A document that overstates its own coverage is worse than one that says nothing: a reader sizing their effort against it is reading fiction. The numbers are gone, the document now points at the runner, and `security_doc_test.py` fails if such a figure ever reappears — because the runner is the only place that knows the true count. This is the same shape as the changelog heading that displayed the previous release's number, and as the README fact frozen at the version the READMEs were stuck at.
  • How this was checked, and what is not claimed: security_doc_test.py holds the new section with 18 checks and 5 mutations, each proved red by putting the defect back: the stale suite total, the deleted safe harbour, a promised $250, the removed disclosure window, a dropped trade-off. The private reporting flag was read back from GitHub, not inferred from the write succeeding. Not claimed: there is no escrow behind this programme and the document says so; the 90-day disclosure window is a commitment this project has made in public and will be held to; dependency CVE status still cannot be verified from this host.

v1.14.3 — White-hat security round: a service foothold could reach root, a backup could disarm every rate limiter, and a rebound host could take the AI provider key

  • The installer could hand a service foothold root: when install.sh is piped, bash has no script path, so the “anchor to the script’s own directory” rule silently fell back to $PWD. A piped install now never uses the working directory, and /opt/zefira is explicitly refused as a source.
  • A crafted backup could disarm every rate limiter: trusted_proxies was importable, and it is the KEY of every per-IP limiter — login brute force, subscription, restore, QR, probe. One attacker /32 in a “customer list” backup made every later request carry an attacker-chosen X-Forwarded-For (unbounded login guesses) and wrote that value into the audit log, so the operator’s own trail pointed at a third party. Like public_url and domain, it is set in Settings only.
  • A leaked API token could replace itself: minting one required no password, so a stolen full token called the same endpoint and received an equally powerful replacement — and revoking the one token the operator could see did not lock the attacker out. Every durable-credential operation now re-prompts for the admin password (as backup, restore and update already did), a new token expires after 180 days unless you ask for otherwise, and one admin may hold at most 20.
  • A rebound AI host could receive the provider key: the base URL was validated, then urllib resolved the name again when it opened the socket.   • One restore request could hold a core for two hours: rows whose credentials cannot be validated are re-provisioned server-side, and an OpenVPN row mints a 2048-bit RSA key. The row cap is 10,000 and nothing bounded the work, so a 12 kB crafted file kept one core busy for close to two hours — and every mutating /api/* route answers 409 while a restore holds the lock, so the whole write plane was down for that long. Re-minting is now budgeted, and the overflow is refused and reported instead of silently dropped. Inbounds are capped too, because each one multiplies a subscription rendered on the unauthenticated path.
  • A crafted backup could repoint the assistant: the AI settings were imported, so a backup could aim the panel at an attacker’s endpoint AND plant text in the system prompt the assistant treats as an ADMIN NOTE — and the next time you asked it anything, the traffic and up to nine tool calls went to the attacker. The whole AI setup is re-entered in Settings now, like the admin credentials.
  • Snapshots were readable by every local user, and never pruned: pg_dump --file and mysqldump --result-file create their output with the process umask, so under the common 0022 the complete database — admin hashes, every customer’s private key, token hashes — was world-readable for the length of the dump. The panel now creates the file itself at 0600, and the dump and pre-update copies are pruned like the SQLite ones. On the docs side: the changelog printed its own emphasis tags as literal text, and every HTML entity in a translation printed as its own characters instead of the character it stands for, frame-ancestors in a <meta> is ignored by browsers (there is a working frame-buster instead), and a protocol-relative knowledge-base link could leave the site silently.
